# 面试讲解与常见追问

## 1. 两分钟项目介绍

这个项目是面向企业内部员工的知识库问答系统。我使用 FastAPI 提供 REST API，PostgreSQL 保存业务数据，pgvector 保存文档向量，Redis 和 Celery 处理文档解析与向量化任务，Streamlit 提供演示界面。

文档上传后会进入异步任务，支持 PDF、DOCX、Markdown 和 TXT。文本经过清洗和重叠分块后生成 Embedding，同时建立 pgvector HNSW 索引和 PostgreSQL GIN 全文索引。问答阶段进行双路召回、RRF 融合、重排序和证据门控，只有证据充分时才调用聊天模型，否则直接拒答。回答会返回来源片段并保存会话、消息、引用、Trace ID 和耗时。

为了验证效果，我构建了 30 条标准问题，评估 Hit@5、Recall@5、MRR@5、引用准确率和拒答通过率。

## 2. 为什么使用 RAG？

- 企业制度会更新，重新训练模型成本高。
- 企业知识通常不能直接进入公开模型训练。
- RAG 可以返回引用，便于员工核对来源。
- 检索层和生成层可以独立评测与调优。

## 3. 为什么混合检索？

向量检索擅长语义相似，但对金额、日期、编号和精确术语不一定稳定；全文检索擅长关键词精确匹配。两者结合可以兼顾语义召回和精确命中。

## 4. 为什么使用 RRF？

向量相似度与全文检索排名分数不在同一尺度，直接加权需要复杂归一化。RRF 只依赖各自排名，容易解释，对分数尺度不敏感。

## 5. 如何降低幻觉？

- Prompt 明确禁止使用知识库外事实。
- 重排序过滤弱相关片段。
- 使用绝对阈值和相对阈值进行证据门控。
- 证据不足时不调用模型，直接返回固定拒答。
- 回答返回引用片段，允许用户核验。

## 6. 为什么使用 Celery 而不是 BackgroundTasks？

Celery 任务独立于 Web 进程，支持 Redis 队列、失败状态、任务持久化和后续横向扩容。FastAPI BackgroundTasks 更适合轻量、短时任务，服务重启时可靠性不足。

## 7. pgvector 与独立向量数据库如何取舍？

当前规模较小，pgvector 可以让业务数据、权限过滤和向量检索位于同一数据库，减少组件数量和一致性问题。数据规模或吞吐明显增长后，可以考虑 Milvus、Qdrant 或 Elasticsearch。

## 8. 如何处理 Embedding 模型维度变化？

系统配置向量维度，并在启动时检查数据库字段。更换维度时重建向量字段和 HNSW 索引，再对历史文档重新向量化。不能把不同维度的向量混存在同一列中。

## 9. 目前最大的不足是什么？

- 扫描 PDF 暂未接入 OCR。
- 重排序仍是规则型，可替换为 Cross-Encoder/Reranker 模型。
- 权限目前是用户所有权隔离，尚未实现部门角色和 ACL。
- 本地文件存储适合作品集，生产环境应迁移到对象存储。
- 当前评测集规模有限，需要真实业务数据持续扩充。

## 10. 如果并发和文档规模扩大怎么办？

- API 多实例部署并引入负载均衡。
- Celery 按解析、Embedding 队列拆分并横向扩容。
- Embedding 批处理、缓存和限流。
- 对象存储替代本地 volume。
- 增加数据库连接池、只读副本和分区策略。
- 当向量规模达到千万级时评估独立向量数据库。
